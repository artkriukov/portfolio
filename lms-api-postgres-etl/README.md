# ETL-пайплайн: API → PostgreSQL
Скрипт забирает из API историю попыток студентов по учебным задачам, очищает и валидирует данные, загружает в PostgreSQL ([Supabase](https://supabase.com/)).

## Проблема

Данные об отправках решений учебных задач поступают из внешнего API в сыром виде и не готовы для прямого анализа. 
Часть полей требует дополнительного преобразования, отдельные значения могут отсутствовать, а повторные запуски загрузки могут приводить к дублированию данных. 
Для дальнейшей аналитики нужен воспроизводимый ETL-процесс, который автоматически собирает, очищает, валидирует и сохраняет данные в PostgreSQL.

## Цель проекта

**Разработать ETL-пайплайн, который:**

- получает из API данные об отправках решений учебных задач по программированию
- приводит их к структурированному и валидному виду
- загружает результат в PostgreSQL
- логирует этапы работы и ошибки в файл с именем по текущей дате и хранит логи только за последние 3 дня
- отправляет email-уведомление о результате запуска
- на подготовленных данных провести анализ активности 

## Что реализовано

ETL-пайплайн состоит из 3 основных этапов:
1. **Извлечение данных**
   - запрашивает данные из API за заданный временной диапазон
   - разбивает период на чанки по дням, чтобы стабилизировать работу и уменьшить риск таймаутов
   - обрабатывает сетевые ошибки и логирует ход выполнения
2. **Нормализация и валидация данных**
   - строковое поле `passback_params` преобразуется в словарь, после чего из ответа API извлекаются поля целевой схемы
   - отсутствующие и лишние значения обрабатываются до этапа валидации
3. **Загрузка в PostgreSQL**
   - подготовленные данные загружаются в PostgreSQL
   - повторная вставка уже существующих записей предотвращается с помощью `ON CONFLICT DO NOTHING`
   - реализована инкрементальная загрузка: пайплайн забирает только новые данные, начиная с последней даты, сохранённой в базе

## Особенности решения

- Логирование настроено на всех ключевых этапах пайплайна: старт, загрузка данных, валидация, запись в БД, ошибки выполнения.
- Логи сохраняются в текстовый файл с именем по текущей дате.
- Автоматически удаляются логи старше 3 дней.
- После завершения работы отправляется email-уведомление со статусом выполнения и краткой сводкой по обработанным данным.
- Временные метки сохраняются в UTC, что делает хранение данных консистентным и удобным для дальнейшего анализа.
- Пайплайн автоматически запускается каждый день с помощью GitHub Actions; также предусмотрен ручной запуск.
- Параметры подключения к API, PostgreSQL и SMTP хранятся в GitHub Secrets.

## Структура данных
Данные сохраняются в таблицу `submissions`:
- `user_id` — идентификатор студента
- `oauth_consumer_key` — уникальный токен клиента
- `lis_result_sourcedid` — ссылка на блок, в котором находится задача в ЛМС
- `lis_outcome_service_url` — адрес сервиса для передачи результата
- `is_correct` — результат попытки: `true`, `false` 
- `attempt_type` — тип действия: `run` или `submit`
- `created_at` — дата и время попытки в UTC
Комбинация `(user_id, attempt_type, created_at)` используется для предотвращения повторной загрузки записей.

## Анализ на основе загруженных данных
На данных из PostgreSQL выполнен exploratory-анализ активности студентов  
([ноутбук](analysis/student_activity_analysis.ipynb))

### Что анализировали
- динамика числа действий и активных студентов во времени
- активность по дням недели и часам (МСК)
- соотношение `run` / `submit` и доля успешных submit
- распределение активности между студентами
- возвращаемость после первого дня активности (D1 / D7 / D30)

### Основные результаты
- За период с 1 июля 2025 по 30 июля 2026 зафиксировано **671 694** события от **4 186** студентов.
- Доля `submit` чуть выше доли `run`: **~54%** против **~46%**.
- Среди submit доля успешных попыток — **~39%**; success rate относительно стабилен во времени, в отличие от объёма активности.
- Активность смещена в дневные часы по МСК; по дням недели ниже в пятницу и субботу.
- Активность распределена неравномерно: медиана действий на студента заметно ниже среднего (медиана **43**, среднее **~160**); группа `200+` даёт большую долю всех событий.
- Retention после первой активности: **D1 ≈ 27%**, **D7 ≈ 13%**, **D30 ≈ 6%**.
